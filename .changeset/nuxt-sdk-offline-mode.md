The server and the browser run from one offline source. `runtimeConfig.configdirector.connection.mode` accepts `offline`, a mode in which the Nitro server client never connects to ConfigDirector and sends nothing, and serves the values of a JSON file named by the new `connection.file` option (also set with `NUXT_CONFIGDIRECTOR_CONNECTION_FILE`, resolved against the server's working directory) or given inline in the new `connection.values` option, to every context, or the in-code default values when neither is given; `serverSdkKey` is not needed in that mode and is still required, with the same error as before, in every other mode. When the values cannot be loaded (a missing, unreadable or non-object file, a value such as `null`, `file` and `values` given together, or either given in `streaming` or `polling` mode) every request fails with a `ConfigDirectorInitializationError` instead of rendering in-code default values, whatever `waitForInitialization` says. When the server runs offline, the module serves `GET /_configdirector/offline-values` with every offline value decoded by config type (404 in every other mode), and the browser plugin fetches it once and runs the browser client in `offline` mode with those values unless `runtimeConfig.public.configdirector.connection` sets its own `mode` or `values`; the browser plugin is now asynchronous, so hydration waits for that response, with `useConfigDirectorStatus` reporting `loading` until it arrives and `ready` right after. The public `connection` accepts `mode: "offline"` and a new `values` option, `clientSdkKey` is not needed when the browser runs offline, and the public `connection.mode` now reads as empty instead of `streaming` when not set (the browser client still defaults to `streaming`). The module writes `runtimeConfig.public.configdirector.serverConnectionMode` on every request so the browser knows the server's mode; it is not an option. The package exports the `OfflineValues` and `OfflineValue` types.
