The new `deferInitialization` option of the public runtime config (`runtimeConfig.public.configdirector.deferInitialization`, or `NUXT_PUBLIC_CONFIGDIRECTOR_DEFER_INITIALIZATION=true`) makes the browser client wait for its first context instead of connecting when the app is created. With it on, nothing connects and nothing is sent, `useConfigDirectorStatus` reports `loading` and configs return their in-code default values until the app calls `updateContext` from `useConfigDirectorContext`; that first call starts the client with the context it was given, so an app that knows its context only after startup, such as one with `ssr: false`, opens one connection carrying the context instead of a first connection with no context, whose visitor counts as a monthly active user on its own. The values kept on the device for that context are served until live values arrive, and the status becomes `ready`, or `default` when the connection timeout passes without values. A context set during server-side rendering still starts the client when the app is created, the option has no effect in `offline` mode, and an installed test client follows the same rules. It defaults to `false`, with no change to apps that leave it off.
