The provider's client keeps the last values it received from ConfigDirector in the browser's `localStorage` and serves them on the next launch of the same context until live values arrive, so an application opened without a network shows the values ConfigDirector last sent instead of the in-code default values. Every evaluation served this way carries the new evaluation reason `cached`, with `isDefaultValue` false. The client is not ready while it serves them: the status stays `loading` and then `default` as before, the provider's initialization still waits for live values or its timeout, and `clientReady` fires when live values arrive; a new `cachedValuesLoaded` event, with a matching hook, fires when the kept values are loaded, together with `configsUpdated`. The new `caching` prop of `ConfigDirectorProvider` and option of `withProvider` turns this off with `enabled: false` or replaces the store with a `CachingProvider` of your own (`read`, `write`, `remove` and `sizeLimit` in bytes), both exported as types; the default store keeps the entry under a key derived from the client SDK key with a size limit of 256 KB, above which nothing is kept. Nothing is kept in `offline` mode.
